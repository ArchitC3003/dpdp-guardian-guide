# Authentication
- Cookie notice stays in document flow on profile setup so small mobile screens scroll to every control.
- Start Google OAuth directly through the generated Lovable helper from the sign-in click, with a synchronous single-flight guard; parallel authorization attempts create independent states.
- Return Google OAuth to the public same-origin `/auth` page and let the session-aware guard enter protected pages; full-page redirects return before session hydration.
- Keep generated integration files unchanged; validate managed popup results with `auth.getUser()` before navigating.
# Learn (public content)
- Public content lives in `content_posts`; anonymous visibility is enforced by RLS (published with `published_at` null or past, or scheduled with `scheduled_for <= now()`), mirrored by `isLive` in `src/lib/content.ts` — keep both in sync.
- Studio saves go only through `rpc_save_content_post` / `rpc_restore_content_version` (SECURITY INVOKER) so post, tags and version snapshot commit atomically under RLS; a BEFORE trigger reserves scheduled/published/archived for admin/moderator.
- `content-media` is a private bucket (public buckets are blocked in this workspace); cover images are stored as long-lived signed links.
- Public lead forms write only through the `submit-lead` function (validation, honeypot, hourly rate limit, consent text stored); never grant anon insert on `marketing_leads`.
- Sitemap/RSS/llms entries for posts are generated live by the `content-feed` function so publishing never needs a rebuild.
- Presentation/video posts store their file in `content_posts.media_*` (private `content-media` signed links); upload limits live in `validateMediaFile` in `src/lib/content.ts` so editor and tests share one rule.
- Learn framework vocabulary lives in the `content_frameworks` table (publishers add values in the editor); `content_posts.frameworks` is validated by trigger and filters match exact values only — never substring-match frameworks.
- The Learn repository is ten fixed domains (`content_domains`) holding topics (`content_topics`); a post has one home topic plus cross-listings in `content_post_topics`, written only by `rpc_save_content_post` from `topic_ids` / `primary_topic_id` in the payload (max 6, mirrored by `MAX_TOPICS_PER_POST`). Filing rules live in `src/lib/content.ts` (`toggleTopic`, `filingError`); never name the source framework for the ten domains in user-facing text.
- Public Learn surfaces use the shared `BrandLogo`. Hover and focus states use `glass-hover` / `glow-hover` in `src/index.css`, except inside the hub index, where `lrn-row`, `lrn-item` and `lrn-chip` carry their own glass-and-glow states (the lens is the hover state for a row); do not stack `glass-hover` on those.
- The public Learn hub offers three ways in, all built from live data: domains, regulations and standards (`content_frameworks`, with `description`), and artefacts to build (`content_artefacts`; a post's `content_posts.artefacts` is validated by trigger and set by `rpc_save_content_post` from `artefacts` in the payload). Adding a framework or artefact in the Content Studio must be enough for it to appear; never hard-code these lists in the hub.
- The hub is built around `LensIndex` (a glass lens that glides to the pointed-at row, with a ring that turns to match) and the `lrn-*` classes in `src/index.css`; `lrn-wrap` gives Learn the same gutters as the landing page. Motion is limited to that signature, responses to a person's action, and one entrance sequence for the index itself (rows rise once on load and when the visitor switches the way in; the panel eases in when its row changes). Do not add entrance effects to other sections, and no all-caps eyebrow labels or card grids on Learn pages.
- "Build it" on a Learn artefact carries the choice through sign-in with `src/lib/buildIntent.ts` (session storage, allow-listed against the builder's `DOCUMENT_TYPES`), and `postSignInPath()` decides where sign-in lands. `content_artefacts.builder_type` holds the builder document type; keep the seeded artefacts aligned with `DOCUMENT_TYPES` in `src/components/policy-builder/types.ts`.
- Listening is automatic: `ListenPlayer` sits in the shared `LearnArticle` template and reads the rendered page through the browser's own speech engine (`src/lib/speech`), so there is no audio field, file or paid service. Mark anything that must not be read aloud with `data-listen-skip`; videos have no player. All playback goes through the one `SpeechController`, never `speechSynthesis` directly.
# Landing page
- The landing page lives in `src/components/landing` with styles in `src/styles/landing.css`, scoped under `.lp` with `lp-` class names; keep them from leaking into the app or Learn. Stage names, status tags and routes come from `stages.ts`; a stage that is not ready has no action.
- A signed-out visitor's stage choice is carried through sign-in: Build uses `saveBuildIntent`, other gated stages use `saveRouteIntent` (allow-listed in `RESUMABLE_ROUTES`, short expiry) in `src/lib/buildIntent.ts`. Add a route to that list before making a new stage resumable.
- The brand palette (warm paper, wheel green, deep pine, coral accent) is defined once in the `:root` tokens of `src/index.css`; the landing page mirrors it in its `--lp-*` variables. The mark is `WheelMark` in `BrandLogo.tsx`.
# Change workflow
- Lovable syncs only `main`, and one Lovable Cloud database serves both live and preview. Every change follows: (1) feature branch with code, Drizzle migration and tests; (2) pull request reviewed and merged to `main`; (3) the Drizzle migration applied to Lovable Cloud from Lovable chat; (4) in Lovable chat: "Confirm commit <hash>, regenerate types, and run verifications".
- Lovable's migration tool writes a new migration file for any SQL it is given and then applies every unapplied file. To apply a migration already in the repo, give it a single comment line; expect one extra empty migration entry.
- Before writing a migration, fetch `origin/main` and number it after the latest file in `drizzle/migrations`.
- `src/App.tsx` pages are lazy (not landing) under `Suspense`; QueryClient: 2-min cache, no focus refetch.
# Consent
- `src/lib/consent.ts` is the single inventory and gate for cookies and browser storage: the banner and `/privacy-preferences` render `CONSENT_CATEGORIES`, and non-essential writes go through `setPreference` / `setPreferenceCookie`. Declare a technology there (and in `GATED_STORAGE` if optional) before storing anything new; never list one that is not in use.
- Fonts are self-hosted from `src/assets/fonts` via `src/styles/fonts.css`; do not add third-party font or script links.
- Rights requests and grievances are written only by the `submit-privacy-request` function (works signed out, validated, rate limited); never grant anon insert on those tables. "Privacy choices" links call `openConsentPreferences()`.
# Consent platform (`cmp` schema)
- The client-facing consent platform lives in its own Postgres schema, `cmp`, with no foreign keys into app tables except `org_members.user_id`. `anon` has no access; visitors reach it only through server functions. Design and specification: "Consent Platform: Stage 1 Technical Design" (Design and Specification tabs).
- Tenant isolation is `cmp.is_member(org_id, role)` in every policy plus triggers that check a row's `org_id` against its site. Members are granted only the columns they may set; platform-owned values (site key, domain token and verification, `purposes.published`, live config) are never member-writable.
- Receipts, seals, flags, config versions, checkpoints and the audit log are immutable for every role; receipts are removed only as whole sealed segments by the retention routine. Never add an UPDATE or DELETE grant on them.
- Any `cmp` migration ships with a reverse script in `drizzle/rollback` and must pass `npm run test:db` (local Postgres: apply, test as each role, reverse, re-apply). Add a check to `drizzle/tests/cmp_schema.test.sql` for every new table or rule.
